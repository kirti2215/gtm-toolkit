# Reflection: ai-agent-iam-blueprint

I spent years building and working with enterprise IAM. The identity provider, the governance platform, the provisioning workflows, the reconciliation jobs, the SIEM integration. The whole stack. And for a long time the underlying assumption held: the entity requesting access was either a human logging in or a service account doing exactly what it was coded to do.

That assumption breaks the moment you introduce an AI agent.

An AI agent is not a service account. It reasons. It retrieves context. It selects tools. It can receive a manipulated input, choose a legitimate tool, observe the result, and continue adapting toward a corrupted objective — with every individual action looking permitted. The sequence is the attack, not the individual call.

That realization is what this repository is built around.

The GitHub starts with a before picture. A traditional cloud enterprise IAM environment: IDP and SSO, identity governance and administration, provisioning and lifecycle management, identity stores, schedulers, reconciliation, SIEM. This is what most mid-size financial services firms actually have. I represented it with a vendor-neutral architecture diagram because the argument is not about any specific platform — it is about the structural assumptions baked into the design.

The second diagram shows what happens when you introduce AI agents into that environment. Five assumptions collapse: identity (an agent is not a human or a deterministic service), authorization (being permitted to call an API is not the same as being safe to call it autonomously), input (a support ticket can contain an instruction that changes what the agent does), audit (logs need to capture reasoning and context, not just which action was invoked), and detection (you now need to detect unusual intent sequences, not just credential abuse).

The third diagram shows the redesigned architecture. Agent identity registry. Tool gateway. External policy enforcement. Approval thresholds. Runtime monitoring. Credential revocation path. The key shift is that the enforcement is external to the agent's reasoning — which it has to be, because an agent that has been influenced cannot be expected to constrain itself.

The fourth diagram, the master operating model, ties it all together across six planes: governance sits at the top where the decision rights and autonomy tier decisions live, threat sits next and grounds the controls in real attack patterns, then the agent identity and delegation plane, then policy and enforcement, then enterprise IAM and resource access, then observability and AI defense. At the bottom is response and recovery, with a feedback loop back up to governance.

The policy engine is where the actual argument gets tested. It is a Python implementation that loads five YAML files at startup and fails closed if anything is missing or malformed. Every proposed agent action goes through a collect-all-then-resolve evaluation: registration check, suspension check, tool approval, action authorization within the tool, resource access, data classification ceiling, delegation validation, explicit deny rules, privileged role name check, volume threshold, injection signal. All violations are collected before the final decision. DENY overrides APPROVAL_REQUIRED overrides ALLOW. No early returns on the non-blocking paths.

The reason collect-all-then-resolve matters is that early returns hide the full picture. If the engine returns DENY on the first violation it finds, you never know what else was wrong. You need the complete signal for the audit log and for the human reviewer who has to make an actual decision.

Four threat scenario tests demonstrate the controls against representative agentic attack patterns: prompt injection via a malicious support ticket shows that the injection scan has to run before any other rule, and its signal has to propagate to every subsequent decision in that evaluation — you cannot have a case where injection is detected and the action still resolves to plain ALLOW. Excessive provisioning via a manipulated batch input shows that volume limits have to be tracked per agent per action in the runtime state, not inferred from logs at evaluation time. Sensitive data overreach shows that denied data and data classification ceiling are two independent checks — a resource can fail either or both. Auto-suspension shows that the suspension trigger is based on the count of prior denials in a time window, not the current call — which means the (threshold + 1)th call is the one that writes the suspension, and the test has to account for that.

The threat model documents the six attack paths: prompt injection, goal hijacking, privilege escalation, data overreach, excessive agency through bulk actions, and the repeated denial pattern that triggers auto-suspension. Each path has an entry point, movement through the architecture, what executes without controls, what the controls intercept, and OWASP and MITRE references. The trust boundary document makes one specific argument that I think is underappreciated: cloud versus on-premises is not the trust boundary for AI agents. An agent crosses both as a normal operating condition. The boundary is identity, policy, and enforced authority — which travel with the agent regardless of where the resource lives.

The strategy layer is where the technical architecture connects to how organizations actually make deployment decisions. The Value times Autonomy times Blast Radius framework asks five questions before deployment: what value does the agent create by acting autonomously, what is the minimum authority required to create that value, what is the worst-case outcome if it is manipulated or wrong, what controls are required at that blast radius, and is the organization ready to support that level of autonomy today. The framework is not a formula. It is the set of questions that do not have good defaults — someone has to answer them explicitly before the agent goes into production.

The decision rights matrix maps who approves, owns, suspends, and accepts residual risk at each autonomy tier. The autonomy tiers run from Tier 0 advisory through Tier 3 privileged. The adoption roadmap sequences the controls so that autonomy expands only when operational evidence supports it — not when someone believes it should, not when a customer requests it, when the audit logs and behavioral monitoring from the current tier show it is warranted.

What building this actually taught me is different from what I expected going in.

The first thing was how much the stopping point question matters architecturally. Before writing the engine, I would have said that a compromised agent is a detection and response problem. After writing it, I think it is primarily a pre-execution enforcement problem. The detection happens too late. The stopping point has to be before execution, external to the agent, loaded from configuration the agent cannot modify.

The second thing was the tool-action separation. Being approved to use a provisioning tool and being authorized to perform a specific action through that tool are two different checks. The gap between those checks is exactly where a clever attacker or a manipulated agent would operate. Modeling them as independent dimensions in the policy engine forced me to think through exactly what the authorization boundary is at each layer.

The third thing was the runtime versus registry separation. When the engine auto-suspends an agent, it writes to runtime state — not back to the YAML registry. The registry is what the agent is configured to be. Runtime state is what happened during execution. Mixing these two corrupts both the configuration management story and the security audit story.

The fourth thing I learned came from thinking about the trust-boundary question. Traditional security discussions often framed trust around infrastructure topology — what was inside the perimeter and what was outside it. Zero trust had already challenged that model, but AI agents make its limitations impossible to ignore. An agent may cross cloud and on-premises boundaries as a normal operating condition. What constrains it is identity, policy, and enforced authority that travel with it regardless of where the resource lives. The deployment environment is not the primary trust boundary. The identity and policy decision are.

The fifth was realizing that autonomy is a risk parameter, not a product feature. Every deployment decision is pricing a trade-off between the value the agent creates and the blast radius if it acts on a corrupted objective. The right question is never what could this agent do if it had broad authority. It is what is the minimum authority required to deliver the stated value, and can we demonstrate that value before expanding it.

A deterministic integration normally follows a fixed script. If its service identity is compromised, an attacker may abuse any permissions attached to that identity. An AI agent adds another risk: it can receive a manipulated input, choose a legitimate tool, observe the result, choose another legitimate tool, and continue adapting toward a corrupted objective — with every individual action appearing permitted. The sequence is the problem, not only the individual calls.

The examples folder captures this in concrete form. The insecure trace shows what executes unchecked: prompt injection goes through, bulk provisioning completes, sensitive data is retrieved without restriction. The controlled trace shows what each enforcement layer intercepts and what decision the engine produces at each step. Both use the same proposed actions — the difference is whether the policy engine is between the agent and the resource.

The fictional enterprise throughout is Veltara Financial Group. Three agents, three autonomy tier assignments, three concrete illustrations of the framework applied. The access review agent can only read and flag — it cannot act on its findings. The provisioning agent can provision standard roles up to a daily volume threshold — privileged role names escalate regardless of the action label used. The security investigation agent requires explicit delegation from a named analyst for every investigation — and its data access is bounded by a classification ceiling even within a legitimate investigation.

This repository is not a complete AI defense platform. It is a reference prototype that demonstrates how the problem needs to be framed and what the minimum viable controls look like when you take that framing seriously. The questions it was built to answer are different from the questions traditional IAM was designed for. Traditional IAM asked: who is this person, and what may they access? This architecture asks: who is this agent, who owns it, on whose behalf is it acting, what information influenced it, which tools may it use, which actions may it propose, where does its authority stop, how do we detect that its behavior changed, and how do we contain it when it does?

That evolution is what the repository exists to demonstrate.
